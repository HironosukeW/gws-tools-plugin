# 管理者の準備（一度だけ）

このプラグインは、**会社で1つだけ作った OAuth クライアント**を全員で共有する前提で設計されている。作るのは Google Workspace の管理権限を持つ人で、作業は一度きりである。以降、利用者が増えても追加の作業はいらない。同じクライアント1つで、スプレッドシート操作（gws）と Apps Script の配置（clasp）の両方をまかなえる。

**このスキルは案内役である。Cloud Console のブラウザ操作は管理者本人が行う。代行しない。** 生成された client_secret.json の中身を表示・複製・送信してもいけない。

## なぜ「内部（Internal）」でなければならないか

同意画面の対象（Audience）を **内部** にできるかどうかで、運用の重さがまったく変わる。ここを外部にすると、あとから全部やり直しになる。

| | 内部（Internal） | 外部（External）＋テスト中 |
|---|---|---|
| Google の審査 | 不要 | 一般公開には必要。Drive のスコープは制限付き扱いなので、有償のセキュリティ評価まで求められる |
| 使える人数 | 組織内なら無制限 | テストユーザー 100 人まで |
| ログインの持ち | 切れない | **7日で切れる**（利用者が毎週ログインし直すことになる） |
| 一度に承認できるスコープ | 制限なし | 25 個程度まで |
| 承認画面 | 通常の画面 | 「このアプリは確認されていません」の警告が出る |

内部を選べるのは、Cloud プロジェクトが会社の組織の下にある場合だけである。組織なしで作ると内部の選択肢が灰色のまま選べない。手順1でそこを確かめる。

## 手順1: Cloud プロジェクトを作る

1. 会社の Google アカウントで [console.cloud.google.com](https://console.cloud.google.com/) を開く
2. 画面上部のプロジェクト選択から「新しいプロジェクト」を選ぶ
3. 名前は用途がわかるものにする（例: `workspace-cli`）
4. **「組織」または「場所」の欄に、会社のドメイン名が入っていることを確認する。** ここが「組織なし」だと、あとで内部を選べない
5. 課金の設定は不要である

## 手順2: API を有効にする

「API とサービス」→「ライブラリ」から、次の5つを検索して有効にする。

| API | 何に使うか |
|---|---|
| Google Drive API | ファイルの検索・アップロード・共有 |
| Google Sheets API | スプレッドシートの読み書き |
| Google Docs API | ドキュメントの読み書き |
| Apps Script API | clasp によるスクリプトの配置 |
| Service Usage API | clasp が上の API の状態を確認するために使う |

Apps Script を使う予定がなければ下2つは省いてよいが、あとから足すより今入れておくほうが手間が少ない。

## 手順3: 同意画面を「内部」にする

「API とサービス」→「OAuth 同意画面」（新しい画面では「Google Auth Platform」）を開く。

1. **「対象（Audience）」タブ → ユーザーの種類を「内部」にする。** ここが最重要である
2. 「ブランディング」タブ → アプリ名を入れる。**この名前が利用者の承認画面に出る**ので、「〇〇社 Workspace CLI」のように、社内の人が見て正体がわかる名前にする
3. サポートメールに管理者のアドレスを入れる

「データアクセス」タブでのスコープ登録は、内部アプリでは必須ではない。承認画面の表示を整えたい場合だけ、次を追加する。

```
https://www.googleapis.com/auth/spreadsheets
https://www.googleapis.com/auth/drive
https://www.googleapis.com/auth/documents
https://www.googleapis.com/auth/script.projects
https://www.googleapis.com/auth/script.deployments
```

## 手順4: デスクトップアプリのクライアントを作る

「Google Auth Platform」→「クライアント」タブ →「クライアントを作成」。

- 種類: **デスクトップアプリ**（ウェブアプリケーションではない。間違えると認証が通らない）
- 名前: 手順3のアプリ名と揃えておく

作成後に「JSON をダウンロード」を押す。`client_secret_〇〇.apps.googleusercontent.com.json` というファイルが落ちてくる。**このファイル名を `client_secret.json` に変える。**

## 手順5: 組織のアプリ制限を確認する

会社が「未設定のサードパーティアプリ」をブロックしている場合、作ったばかりのクライアントも弾かれる。管理コンソールで確認する。

1. [admin.google.com](https://admin.google.com/) →「セキュリティ」→「アクセスとデータ管理」→「API の制御」
2. 「未設定のサードパーティ アプリ」が「アクセスをブロック」になっているかを見る
3. ブロックしている場合は、「サードパーティ アプリのアクセスを管理」→「アプリを追加」→「OAuth アプリ名またはクライアント ID」から、手順4のクライアント ID を検索して**信頼済み**として登録する

ブロックしていない組織では、この手順は不要である。

## 手順6: 対象表シートを作る

操作してよいスプレッドシートの一覧を、Google スプレッドシート1枚で管理する。作り方は、このプラグインの `config/registry-sheet-format.md` に書いてある。

このシートを直せば全員に反映されるので、対象の追加や書き込み可否の変更でプラグインを配り直す必要はない。利用者には**閲覧者**として共有する。

## 手順7: 利用者へ配る

利用者ひとりずつに、次の2つを渡す。

| 渡すもの | 渡し方 |
|---|---|
| `client_secret.json` | 社内の Drive で共有する。**公開リポジトリ・チャットの公開チャンネル・メールの一斉送信には置かない** |
| 対象表のスプレッドシート ID | プラグインの設定画面に貼り付けてもらう値である |

デスクトップアプリのクライアントシークレットは、Google 自身が「インストール型アプリでは秘密として扱えない」としているもので、漏れたら即事故という種類のものではない。それでも社外に置く理由はないので、社内で閉じた経路で配る。

利用者側の作業は `gws-setup` スキル（スプレッドシート用）と `clasp-setup` スキル（Apps Script 用）が案内する。管理者は「Claude に『セットアップして』と言ってください」と伝えればよい。

## あとから困らないための記録

管理者は次を控えておく。利用者が「確認されていないアプリ」の警告を見た、数日で認証が切れる、といった相談をしてきたときに、ここを見れば原因がわかる。

- Cloud プロジェクト名とプロジェクト ID
- OAuth クライアント ID（末尾が `.apps.googleusercontent.com`）
- 対象（Audience）を内部にした日付
- 管理コンソールで信頼済みに登録したかどうか
